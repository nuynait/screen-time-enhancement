# Design log

Append new decisions at the bottom, including failures and what was actually verified.

## 2026-09-08 — First implementation

**Request.** Create a standalone iPhone app that makes opening distracting apps require a two-digit multiplication problem, then grants 15 minutes of access. The initial defaults are one correct answer and one app per window.

**Architecture.** Native SwiftUI app plus Shield Action, Shield Configuration, and Device Activity Monitor extensions. The app uses individual Family Controls authorization. Selected applications remain shielded except for active per-app grants. No backend or API keys are needed. Target iOS 17.0 for the existing SwiftUI API surface.

**SDK finding.** Xcode 26.3 (17C529)'s ManagedSettings Swift interface lacks `openParentalControlsApp`. Apple's current documentation marks that case as introduced in iOS 26.5. Runtime `#available` alone cannot compile a symbol missing from the SDK, even if the target phone is newer. The project generator detects the SDK symbol and sets a custom compilation condition. Both SDK and runtime gates protect the direct response. Older builds queue a local notification and close the protected app; their shield copy also explains manual opening of Gate. Upgrading Xcode and regenerating is necessary to build the direct handoff. Do not replace this with a guessed enum raw value.

**Device tooling.** Development encountered a phone whose developer disk image could not be mounted. Discovery of a device does not prove that Xcode can run code on it. Physical-device validation needs functioning device support and provisioned targets; simulator checks can proceed independently.

**Privacy and routing.** Store Apple's opaque `ApplicationToken`s. Maintain local UUIDs for stable rows and per-app grants. A shield action stores the token's UUID as a pending challenge, and Gate consumes it on activation. Pending requests expire after ten minutes. The application picker is explicit-app-only: whole categories and domains are rejected instead of appearing protected when they aren't. Do not infer readable app names or invent URL schemes. After solving, the user returns with the app switcher/Home Screen.

**Expiry.** A correct answer registers a unique Device Activity schedule before persisting an unlock and removing its shield. Scheduling errors leave the shield on. The grant lasts exactly 900 seconds from issuance. Device Activity uses whole date components: the registered interval starts one second earlier and rounds the end up, satisfying Apple's fifteen-minute minimum while never ending before the stored expiry. Date components include a UTC timezone and full date to handle midnight and daylight-saving transitions. OS delivery itself is not exact. Expiry callbacks recompute shields from current grants, preserving any newer window when an old callback arrives. Foreground reconciliation and the next solve prune old monitor registrations.

**Persistence and concurrency.** Store JSON in one App Group. `flock` on a separate lock file serializes full read-modify-write transactions across processes, including the resulting ManagedSettings update. Atomic replacement protects the state file. A corrupt file throws; it does not reset selections or clear existing system shields. Device Activity calls happen outside this lock because Apple documents that monitoring can immediately invoke extension callbacks. Plain UserDefaults or one actor per process would not give this ordering.

**Design direction.** Quiet calculation sheet with one prominent multiplication expression; rounded system type makes it approachable without a gamified feed. Palette: paper blue `#F2F7FF`, ink `#21385C`, action blue `#2E59C2`, muted slate `#5C6E8C`, dividers `#CCD9F0`, with matching dark variants. Left-align setup and app rows; center the arithmetic and answer. The home screen shows app state and a compact unlock action. Avoid streaks, rewards, decorative dashboards, or scroll-inducing content. The icon is drawn reproducibly from Swift/AppKit as doorposts around a multiplication sign.

**Verification approach.** Foundation-only Swift package checks products, expiry boundaries, app isolation, stale grants, persistence, corruption, and concurrent writes. XCUITest drives a wrong answer, a correct answer, cancellation, and early locking through the same challenge UI in an explicit Debug preview. Preview is labeled and never constructs the real Screen Time service. It cannot prove system enforcement. The physical test matrix remains a separate acceptance gate.

**Initial test failure.** `XCTAssertNoThrow` around the mutation inside `DispatchQueue.concurrentPerform` caused Swift to infer a throwing worker closure, which that API rejects. Replaced it with explicit `do/catch` and `XCTFail`. This was a harness compile issue; tests had not executed yet. The first simulator app build succeeded, then notification delegate isolation/import annotations were tightened to remove Swift concurrency warnings.

## 2026-09-08 — Configurable unlock time

**Behavior.** Added Settings → Unlock time with 1, 3, 5, 10, 15, 30, and 60 minutes. Fifteen minutes remains the default. Each calculation captures the current preference when it opens, so its explanation, unlock button, and resulting grant agree. Changing the setting applies to new calculations and never changes an existing grant's stored dates. Home copy follows the preference. The system shield and notification use duration-neutral wording so a cached message cannot promise an old duration.

**Storage compatibility.** `GateState` remains version 1 with an optional `unlockDurationMinutes` integer. Missing or unsupported numeric values resolve to 15 minutes; malformed values still surface a storage error. Existing grants continue decoding their original `issuedAt` and `expiresAt` fields. Preference writes use the existing locked JSON transaction without touching shields or monitors. Debug preview changes only its in-memory state and resets on relaunch.

**Short windows.** Apple documents a [minimum total monitoring interval of fifteen minutes](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/monitoringerror/intervaltooshort) and permits [starting monitoring during an ongoing interval](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/startmonitoring(_:during:events:)). For short grants, `UnlockSchedule` places the start further in the past so the full interval exceeds the minimum; it keeps the upcoming end at the selected expiry, rounded up to the next whole second. This is an implementation inference from those APIs, not confirmation of real-device callback delivery. Registration still happens before unshielding and outside the storage lock. The monitor has no interval-start behavior. The physical checklist now explicitly includes 1-minute and 5-minute background expiry.

**Tests and an accessibility finding.** Added coverage for every supported duration, schedule bounds across midnight/DST, duration decoding, migration from old state, and preference persistence without rewriting grants. An iOS test checks `DeviceActivitySchedule.nextInterval` against the desired expiry for every duration without registering monitors or requesting authorization. These state/API checks live alongside UI tests because the persisted model imports iOS-only Family Controls types. The new interaction test changes to five minutes, solves, changes to thirty minutes, verifies the original countdown remains short, and opens a new thirty-minute calculation. Its first runs exposed that the home countdown's custom accessibility label hid the remaining time and provided an empty value. Added an explicit timer `Text` as the accessibility value and made the test read that value.

**Verified.** All 13 core tests and all 6 simulator tests (3 state/API checks and 3 UI flows) pass. Simulator testing builds the app and all three extensions. A signed Debug iPhone build of all four targets also passes with the existing local signing configuration. Only Xcode's informational App Intents metadata-skipped warnings remain. Inspected the Settings screenshot and saved it in `docs/screenshots/settings.png`; the README explains the new choices and their effect on existing windows. Whitespace, README local links, and a scan of changed files for private signing identifiers/local paths pass. Physical-device enforcement, including expiry of the short windows, remains unverified.

## 2026-09-08 — Notification permission guidance and Settings handoff

**Behavior.** The home screen's Opening a calculation block now depends on the current notification authorization. It appears only for `.notDetermined` or `.denied`, after Screen Time authorization and only when the notification handoff is needed. Authorized, provisional, and ephemeral notification permissions hide it. Gate reads the OS status on first appearance, after Screen Time setup, and whenever it becomes active. It requests the first notification permission automatically after Screen Time setup; it never automatically opens Settings or requests again after denial. Both permission buttons open notification settings on a later tap when a decision already exists. The Settings screen offers Notification settings after permission is granted.

**System APIs.** Apple's [authorization request documentation](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/requestauthorization(options:completionhandler:)) says only the first request shows a prompt. Read `UNUserNotificationCenter.notificationSettings()` rather than caching a Boolean in Gate's state file. Use [`UIApplication.openNotificationSettingsURLString`](https://developer.apple.com/documentation/uikit/uiapplication/opennotificationsettingsurlstring) for the app's notification page, with the general app-settings URL as a fallback if opening fails. Declining the initial prompt leaves the guidance visible without a second error alert or immediate Settings redirect. One in-flight guard prevents scene activation and button taps from starting overlapping permission requests.

**Preview and tests.** Ordinary Debug preview uses a sample authorized status and requests no system permission. Only the explicit combination `--demo --uitesting --test-notifications` exercises real notification permission while keeping Screen Time enforcement in preview mode. The UI test uses the real system prompt and Settings app. Fresh, isolated test identifiers were used for both Allow and Don't Allow; `TEST_RUNNER_GATE_NOTIFICATION_TEST_RESPONSE=allow` selects Allow for that first request, while later runs reuse the OS decision.

**Simulator limitation found.** The initial test expected Settings to expose an Allow Notifications switch and failed. Inspection showed that this simulator opens the Settings home screen and has no per-app notification toggle. Kept the public notification-settings URL; the test now checks actual Settings foregrounding, the absence of another permission prompt, and the current guidance after returning. Permission changes made in Settings must still be checked on a physical phone. The accepted and denied first-request paths can both be tested on fresh simulator installations.

**Verified.** All 7 simulator tests pass (3 state/API tests and 4 UI flows), including a fresh Don't Allow response. A separate fresh installation passed the Allow path. Both builds use the real User Notifications API. Inspected the initial system prompt, home guidance after denial, and updated Settings screenshot; saved them under `docs/screenshots/`. Signed Debug iPhone build of all four targets passes with the existing local signing overrides. No Swift warnings; only Xcode's App Intents metadata-skipped messages. Whitespace, private-identifier scan, and README links pass. Core policy/storage code is unchanged, so the previously passing 13 core tests were not repeated. Physical-device notification toggling, shield handoff, and expiry remain open on the device checklist.

## 2026-09-08 — Fresh calculations after leaving Gate

**Request.** Prevent carrying a calculation into Calculator and returning with its answer. Any unfinished app, practice, or Settings challenge is marked invalid when Gate leaves the active scene phase (including an inactive transition such as Control Center). Returning active replaces both operands and the answer, keeping the originally offered operation, digit sizes, and unlock duration. The replacement keeps arithmetic constraints, including exact whole-number division, and explicitly rejects the previous answer. A short note explains why the calculation changed.

Every round carries its calculation preferences; foreground refresh never silently adopts changed preferences. Renewal creates a new session identity, and the challenge view uses that identity so its answer, feedback, focus, and success state reset together. Submission rejects stale/invalidated sessions and duplicate completions. The model records completed session IDs so completed practice/app results and running grants survive app switching unchanged. Settings access still ends on backgrounding, but an unfinished Settings challenge now stays on the challenge path and renews on return rather than being discarded.

The simulator does not contain Calculator, so the UI flow opens the system Settings app to exercise a real app switch, then checks new numbers, empty input, disabled submission, rejected old answers, and successful new answers for all three destinations. It also backgrounds a completed app challenge to verify that success and the existing countdown remain.

## 2026-09-09 — Emergency passcode held by a trusted person

**Request and scope.** Settings can configure an optional four-digit passcode for a parent or friend to keep. Setup asks for the code twice, accepts leading zeros, and has no default. Every unfinished calculation offers Emergency bypass once configured. A correct code completes that particular app, Settings, or practice gate. App access uses the challenge's captured duration; Settings and practice never create or extend grants. The success screen identifies passcode access without showing an answer or claiming the calculation was solved.

**Credential boundary.** The app-only credential uses Apple's generic-password Keychain API with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` and synchronization disabled. See [Apple's accessibility contract](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlockedthisdeviceonly). Extensions need grant state, not this credential, so it is deliberately separate from `LockedJSONStore` and never appears in the shared JSON file. Keychain updates replace the item in place; failed reads, malformed saved values, and failed writes propagate errors rather than enabling bypass or overwriting an existing code. Preview credentials use an isolated in-memory store and disappear on relaunch. No credential is placed in a launch argument, screenshot, or diagnostic message.

**Editing and lifecycle.** Changing or removing the code requires the existing code even after entering Settings with math; the final replacement rechecks it. Secure fields mask input and clear unfinished entry, candidate codes, and feedback whenever the scene leaves active. The existing challenge refresh discards the attached passcode sheet and changes both operands and answer on return. Both math and passcode completion validate the same current, unfinished session and use the same schedule-before-unshield path. Settings presentation also checks the active scene at the deferred sheet handoff, so a dismissal that completes in the background cannot open Settings there. There is no permanent lockout or mathematical fallback for changing the credential; the ordinary calculation remains available if the code is forgotten. This remains a local friction tool, not remote or tamper-proof parental management.

**Presentation.** The Settings section explains who should keep the code and what its window means. Setup uses a short choose/confirm sequence; change first verifies the current code. The challenge's secondary key button leads to a masked, explicitly submitted entry screen whose primary action states the destination or duration. The existing rounded typography and blue palette are preserved, with scrolling content for large text and the numeric keyboard.


**Findings during verification.** The initial UI pass exposed a countdown assertion that read the custom “Time remaining” accessibility label instead of the countdown itself; the test now reads the success screen's timer. A live screenshot also showed the submit button partly under the numeric keyboard, so passcode submission now sits in a bottom safe-area inset and stays fully visible while the form scrolls. The initial Keychain integration test failed with `errSecMissingEntitlement` in the unsigned UI runner. Enabling ad-hoc signing alone still left that runner without an application identity. Adding simulated entitlements to the test bundle did not give them to XCTest's prebuilt runner, and forcing them into its actual signature prevented launch. Those temporary entitlement overrides were removed. The integration test now belongs in a standard app-hosted unit target, where the app provides the simulator entitlement context. The test action explicitly launches the host with `--demo`; the fixture uses a unique Keychain service and removes its item afterward. UI automation continues in its separate runner.

App-hosted tests verify real simulator Keychain add/read/update/delete operations and protection attributes, wrong/stale/duplicate submission rejection, app isolation, the captured five-minute duration after preferences change, and unchanged grants after Settings/practice bypass. These three hosted tests also pass with generic bundle/App Group identifiers and an empty development team, confirming the ad-hoc simulator setup needs no developer account. The final signed Debug iPhone build of all four targets succeeds. Ordinary Run has no demo argument; only the test action supplies it.
